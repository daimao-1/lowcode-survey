「这是一个可视化问卷搭建平台。核心解决的问题是：让不会写代码的人也能做出结构复杂的问卷，并且做完能直接导出 PDF、发链接给别人答题。

02全景：一份问卷的数据怎么流动

它解决什么问题

低代码编辑器本质上是同一份数据被三个地方同时消费：左边的目录要显示题目、中间画布要渲染控件、右边面板要显示可编辑项。如果三处各自维护一份状态，改一处另外两处就不同步。

所以整个项目的架构只有一条主线：一份 coms 数组是唯一数据源，三个面板都是它的只读投影，所有修改都从右边面板发起、写回数组、再驱动三处重渲染。

这张图能顶三分钟

面试时如果白板讲架构，就画这个。三个框一画，一句"唯一数据源，三个只读投影，修改统一出口"，架构就讲完了。比说一堆技术名词有效得多。

03地基：Status 到底是什么

它解决什么问题

问卷里每一道题都长得不一样：单选题有选项、评分题有星星、文本题有输入框。但它们又共享一堆东西——标题、描述、对齐方式、字号、加粗、颜色。

如果给每种题型写一个独立的数据结构和一套属性面板，30 种题型就是 30 套代码。所以这里做了一个抽象：每道题 = 一个组件 + 一份"它有哪些可配置项"的描述。这份描述就是 status。

src/types/common.ts 
7export interface Status {
8  type: VueComType                       // 真正渲染的 Vue 组件
9  name: Material                        // 字符串标识，如 'single-select'
10 id: string                            // 唯一 id，拖拽排序靠它做 key
11 status: {
12   [key: string]: TextProps | OptionsProps
13 }
14}
字段白话
type这是"渲染器"。画布上 <component :is="type"> 直接把它渲染成单选/多选/输入框。
name这是"身份证"。因为组件对象没法存进数据库、也没法序列化，所以另存一个字符串来标记"我是哪种题"。后面所有麻烦都出在这里。
id拖拽时 Vue 需要稳定的 key。用数组下标当 key 会导致拖动后组件状态错乱。
status一个对象，每个 key 是一个可配置项。它不只是"值"，还自带"用哪个控件来编辑我"。

status 里每一项长什么样

src/types/editProps.ts 
3export interface BaseProps {
4   id: string
5   isShow: boolean        // 这一项要不要显示在属性面板里
6   editCom: VueComType    // 用哪个组件来编辑它 ← 关键设计
7   name: string
8 }
这一行是整个项目最值钱的设计：editCom 把"数据"和"编辑它的界面"绑在了一起。所以属性面板不需要知道"标题该用什么输入框、字号该用什么下拉"，它只要遍历 status，把每一项交给该项自带的 editCom 去渲染就行。

04加一个题型，为什么只改一处

它解决什么问题

低代码编辑器最大的维护成本不是写功能，是加功能。如果加一种题型要动画布、动属性面板、动大纲、动导出白名单……加五种之后代码就没人敢碰了。

这个项目的目标是把"加题型"收敛成三个动作：写组件 → 写工厂 → 注册映射。别的都不用动。

动作一：写一个工厂，描述这道题的默认长相

src/configs/defaultStatus/SingleSelect.ts（节选） 
14export default function (): Status {
15  return {
16    type: markRaw(SingleSelect),
17    name: 'single-select',
18    id: uuidv4(),
19    status: {
20      title: { id: uuidv4(), status: '默认单选题标题',
21               isShow: true, name: 'title-editor', editCom: markRaw(TitleEditor) },
22      options: { id: uuidv4(), currentStatus: 0,
23                 status: ['选项1','选项2'],
24                 editCom: markRaw(OptionsEditor), ... },
25      // …position / titleSize / descSize / titleWeight / titleColor 等
26    },
27  }
28}
写法为什么非得这么写
markRaw(...)不加的话 Vue 会把组件对象变成响应式代理。组件对象被 proxy 包一层之后问题很多：性能白掉、=== 比较失效、拖拽时可能报递归更新。凡是"不会变的对象"都该 markRaw。
函数返回新对象每拖一次要一道新题。如果导出的是常量对象，两次拖拽会共享同一个引用，改一个另一个跟着变。
每个子项都有 id: uuidv4()属性面板 v-for 需要 key。用 index 当 key，增减选项时会复用到错误的 DOM。

动作二：注册到映射表

src/configs/componentMap.ts 
27export const componentMap: ComponentMap = {
28  // 业务组件（题目）
29  'single-select': markRaw(SingleSelect),
30  'multi-select': markRaw(MultiSelect),
31  'text-input': markRaw(TextInput),
32  'rate-score': markRaw(RateScore),
33  // …共 25 个题型名 + 12 个编辑组件
34  // 编辑组件（属性面板用）
35  'title-editor': markRaw(TitleEditor),
36  'options-editor': markRaw(OptionsEditor),
37}

这张表有两个用途，很关键，分开记：

  1. 按 name 找组件——从 IndexedDB 读回来时，靠它把字符串 'single-select' 还原成真正的组件对象。
  2. 按 name 找编辑控件——属性面板渲染 status.title 时，用它的 editCom 字段，而 editCom 本身也是从这个表里取的。

动作三（可选）：加进组件市场分组

src/configs/SurveyGroupConfig.ts 里决定它出现在左侧目录的哪个分组、显示什么名字。这一步纯展示，不影响功能。

怎么答

如果面试官问"你的可扩展性体现在哪"，不要只说"我做了 30 种题型"，要说：

「新加一种题型，我只写一个组件和一个配置工厂，然后在 componentMap 里加一行。画布、属性面板、大纲、导出白名单都不用改——因为画布是按 type 动态渲染的，属性面板是按 status 里的 editCom 动态渲染的，两者都不认识具体题型。」

05画布：渲染、拖拽、大纲联动

它解决什么问题

画布要同时满足三件事：按顺序渲染每道题、能拖动排序、拖动时左边大纲要跟着动、点大纲时画布要滚到对应位置。

难点在双向同步：如果画布和大纲各自维护一个数组，拖动画布后大纲就错位了。

src/views/EditorView/Center.vue 
3<draggable v-model="store.coms" item-key="index" @start="dragstart">
4  <template #item="{ element, index }">
11    <div :key="element.id" @click="clickHandle(index)">
14      <component :is="element.type" :status="element.status" />
15    </div>
16  </template>
17</draggable>
这一行在干嘛白话
v-model="store.coms"不是绑一个本地数组，而是直接绑 store 里的数组。所以拖动结束的一瞬间，store 里的顺序就变了 —— 大纲读的是同一个数组，自然同步，不需要任何 watch 或事件通知。这就是"唯一数据源"带来的好处，也是为什么不能各自维护一份。
item-key="index"vuedraggable 内部用的标识字段。注意真正的 DOM key 是下一行的 element.id。
:key="element.id"Vue 靠 key 判断"这是同一个组件还是新组件"。用数组下标当 key，拖到第二位后原本第二位那道题的组件实例会被复用，导致输入框里的光标、内部状态错乱。
:is="element.type"动态组件。画布完全不认识 single-select 还是 rate-score，它只知道"这有个 type 字段，把它渲染出来"。
:status="element.status"把整份配置传给子组件。子组件内部自己决定怎么用（标题放哪、选项怎么排、颜色取哪个）。

大纲为什么能跟着动

src/views/EditorView/LeftSide/Outline.vue 
2<draggable v-model="store.coms" item-key="index">
9  <div v-show="isSurveyComName(element.name)">
11    {{ serialNum[index] }}. {{ element.status.title.status }}
12  </div>
13</draggable>

注意它也是 v-model="store.coms" —— 同一份数组，绑了两次。所以：

  • 在画布拖动 → 数组变了 → 大纲重渲染 ✅
  • 在大纲拖动 → 数组变了 → 画布重渲染 ✅

不需要写任何同步代码。

两个容易讲错的地方

① v-show 不是 v-if：大纲里"备注说明"这类非题目组件不显示序号，但它在数组里占位。用 v-show 是为了保持 index 与数组一一对应；换成 v-if 后 DOM 里的位置就对不上了。

② 序号是算出来的，不是存的：题目编号来自 useSurveyNo(store.coms)，它遍历数组，只在"是题目类型"的位置递增计数器，非题目组件返回 null。所以删掉中间一道题，后面编号自动前移，不用手动维护。

06属性面板：12 行代码驱动 15 个控件

它解决什么问题

单选、多选、评分、日期……每种题的属性面板长得不一样。如果给每种题写一个面板组件，30 种题型就是 30 个面板，其中 80% 的控件是重复的。

这里换了个思路：不给题型写面板，让题型自己声明"我有哪些属性、每项用谁编辑"。面板只负责遍历。

整个面板的全部渲染逻辑：

src/components/SurveyComs/EditItems/EditPannel.vue 
3<div v-for="(item, key) in com.status" :key="item.id">
5  <component
6    v-if="item.isShow"
7    :is="item.editCom"
8    :config-key="key"
9    v-bind="item"
10  />
11</div>
写法白话
v-for="(item, key) in com.status"遍历这道题的所有配置项。注意拿到的是 key（'title' / 'titleSize' / 'options'…），不是下标。
v-if="item.isShow"有些属性要按条件隐藏。比如文本题切换成"多行"时，会把标题/描述等其他配置项整体隐藏（dispatch.ts 的 setType 里一次性翻转所有 isShow）。
:is="item.editCom"这一项自己带着"用谁编辑我"。面板不认识任何具体控件。
:config-key="key"必须传，别漏。因为 titleSize 和 descSize 共用同一个 SizeEditor，控件必须知道"我在改的是哪一个"。这就是图 2 里标红的那句。
v-bind="item"把整项（含 status / currentStatus 等）平铺成 props 传下去。省掉逐个绑定。
这段是全场最强的一句

面试时可以说：「属性面板我没有按题型写，我做的是数据驱动——每道题自己声明有哪些可配置项、每项用哪个编辑控件，面板只做一次遍历。所以 30 种题型共用同一套面板代码，面板文件总共 12 行。」

如果被追问"那新增一种编辑控件怎么办"：答"写一个组件，在 componentMap 里注册，然后在题型的工厂里把某一项的 editCom 指向它，面板不用改"。

07改一个属性，中间发生了什么

它解决什么问题

属性面板里有输入框、下拉、颜色选择器、增删按钮……如果每个控件都直接去改 store，就得写十几种改法，而且类型判断散落各处。

这里的做法是收口：所有控件都只发一个 updateStatus(configKey, payload)，由 dispatch 一处做类型分派，再调用对应的 action。

src/views/EditorView/Index.vue 
50const updateStatus: UpdateStatus = (configKey, payload, isShowChange) => {
55  if (store.currentComponentIndex === -1) {
57    ElMessage({ message: '请先将组件处于编辑状态', type: 'warning' })
59    return
60  }
63  const status = store.coms[store.currentComponentIndex].status
66  dispatchStatus(store, status, configKey, payload, isShowChange)
67}
68provide('updateStatus', updateStatus)

白话：这个函数是整个编辑器唯一允许改数据的地方。它做三件事：检查有没有选中组件（没选中就提示并拒绝，避免改到不存在的题）、拿到当前选中题的 status、交给 dispatch。

最后一行 provide 把它注入下去，任何层级的子组件都能 inject 拿到它，不用一层层 props 传。这就是"收口"的物理实现。

dispatch 在干什么

src/stores/dispatch.ts（节选） 
27switch (configKey) {
39  case 'title':
40  case 'desc':
41    if (typeof payload !== 'string') { console.error(...); return }
45    store.setTextStatus(status[configKey], payload)
46    break
47  case 'options':
49    if (typeof payload === 'number')      store.removeOption(...)   // 删选项
56    else if (typeof payload === 'boolean') store.setUse(...)        // 启用/禁用
58    else if (isOptionsStatusByIndexPayload(payload)) store.setOptionsStatusByIndex(...)
63    else                                  store.addOption(...)     // 加选项
66    break
106  default: console.warn(`Unknown configKey: ${configKey}`)
109}
这段是面试的高价值点

注意 options 这个分支：同一个 configKey，靠 payload 的类型区分意图——传 number 是删选项、传 boolean 是切换启用、传带 index 的对象是改某个选项的文字、传 undefined 是新增。

为什么这么设计？因为属性面板里"选项"这一块有四种操作（增、删、改文字、启用禁用），但它们改的是同一个字段。与其开四个入口，不如一个入口靠载荷类型分派。

被问"为什么不给每种操作单独写一个方法"时，答：「面板和 store 之间只保留一个通道，减少耦合面，也让"未选中组件"这类前置校验只需要写一处。」

另外每个分支开头都有 typeof payload !== 'xxx' 的判断。这不是啰嗦——TypeScript 的类型在运行时全部消失，这些判断是运行时的最后一道防线。配合 types/ 里那一堆 isXxx() 类型谓词函数，才既让编译器满意、又让运行时安全。

08双 Store：一套逻辑伺候两个场景

它解决什么问题

项目有两个场景：编辑器（一堆题排成一条线）和组件市场（左目录选一种题型，右边单独试玩一个）。

这两个场景的交互逻辑是一模一样的：改标题、加删选项、调字号颜色……唯一区别是编辑器操作"数组里的某一项"，市场操作"当前选中的那一个题型"。

如果写两套，改一个 bug 要改两处，而且两边行为会慢慢跑偏。

src/stores/useStore.ts（全文 19 行） 
6export default function () {
8  const activeView = localStorage.getItem('activeView')
9  switch (activeView) {
10    case 'materials': return useMaterialStore()
14    case 'editor':    return useEditorStore()
18  }
19}

白话：这是一个"门卫"。组件不直接 useEditorStore() 或 useMaterialStore()，而是调 useStore()，由它根据当前处在哪个视图，把对应的 store 交出去。

关键在于两个 store 实现了同一套 Actions 接口：

src/types/store.ts 
30export interface Actions {          // 共用的一套动作
31  addOption, removeOption, setPosition, setSize,
32  setWeight, setItalic, setColor, setTextType,
33  setTextStatus, setUse, ...
36}
38export interface MaterialStore extends Actions { ... }
52export interface EditorStore  extends Actions { ... }

所以 dispatchStatus(store, ...) 的参数类型是 EditorStore | MaterialStore——它在两个场景下是同一份代码。

怎么答

「编辑器和组件市场我用了两个 Pinia store，但它们共用同一套 actions 接口，通过一个 useStore() 按当前视图动态返回实例。这样 dispatch 那层的分派逻辑只写了一份，两个场景行为永远一致。」

讲的时候必须补一句实话：这套设计有个已知弱点——依赖 localStorage.activeView 这个隐式状态，而且 useStore() 在没有匹配值时返回 undefined。更稳的做法是把视图类型放进路由 meta 或用 provide/inject，而不是读 localStorage。

主动说出自己方案的弱点，比被面试官挑出来强得多。这句话说出来，评价通常是"这人有代码审视能力"。

09存进 IndexedDB：组件为什么会丢

它解决什么问题

需求是"关掉页面再打开，我的问卷还在"。所以要把 coms 存到浏览器本地。

但 Status 里的 type 和 status[*].editCom 都是Vue 组件对象。而 IndexedDB 存数据用的是结构化克隆（structured clone），这套算法的规则是：函数、DOM 节点、class 实例一律不能克隆，遇到就抛 DataCloneError。

所以直接存会炸。

解法：存之前把组件丢掉，读的时候按 name 补回来

src/utils/dboperate.ts（保存） 
23const surveyToSave = {
24  createDate: ..., updateDate: ...,
25  title: value,
26  surveyCount: store.surveyCount,
27  coms: JSON.parse(JSON.stringify(store.coms)),   // 关键这一行
28}

白话：先 stringify 再 parse，等于"深拷贝一份但是只保留能被 JSON 表达的东西"。组件对象在 stringify 时被丢掉（或变成 {}），存进去的就只剩纯数据。

src/utils/index.ts（还原） 
107export const restoreComponentStatus = (coms: Status[]) => {
108  coms.forEach((com) => {
109    com.type = componentMap[com.name]              // 按题型名找组件
110    for (const key in com.status) {
111      const name = com.status[key].name              // 如 'title-editor'
112      com.status[key].editCom = componentMap[name]   // 按控件名找编辑器
113    }
114  })
115}
这段是全场技术含量最高的一段

面试如果问"你遇到过最难的技术问题"，用这个。完整答法：

「我一开始直接把整个对象塞进 IndexedDB，报 DataCloneError。查了才知道结构化克隆不支持函数。所以改成落库前先做一次 JSON 序列化，把组件字段丢掉、只留 name 字符串。读取的时候再按 name 从 componentMap 里把组件查回来，重新挂到 type 和 editCom 上。

这里踩过一个坑：JSON.stringify 处理组件对象不是把它删掉，而是变成 {}。所以我一开始写的"如果 type 为空才补"这个判断是失效的——它不为空，只是变成了空对象。后来改成无条件覆盖才对。」

顺带：为什么用 IndexedDB 而不是 localStorage

维度localStorageIndexedDB
容量约 5MB，超了直接抛异常通常几百 MB 起，按域名配额
数据类型只能存字符串结构化克隆，能存对象/Blob/ArrayBuffer
操作方式同步，会阻塞主线程异步，不卡 UI
查询自己 parse 后遍历有索引、游标、范围查询

这份项目里问卷带 base64 图片后很容易超过 5MB，所以必须用 IndexedDB。而"发布分享"那点小数据用 localStorage 就够（utils/demoStore.ts 就是干这个的）。

10导出 PDF：为什么不截图

它解决什么问题

用户要一份 PDF 版问卷拿去打印或发人。常见做法是 html2canvas 把页面截成图片再塞进 jsPDF。

这个项目没用那种方案，走的是浏览器原生打印通道：window.print() + @media print 样式，用户在打印对话框里选"另存为 PDF"。

92    ElMessage({ message: '存在不支持PDF导出的组件，请先移除这些组件', type: 'warning' })
93    return
94  }
96  window.print()
97}

179  .no-print { display: none; }        // 隐藏返回/导出按钮
181  .no-border { border: none; box-shadow: none; }  // 去掉卡片边框阴影
182}

两条路线的真实差别

canvas 截图 + jsPDFwindow.print（本项目）
文字质量变成位图，放大就糊矢量文字，放大不糊
能否选中/搜索不能，是一张图能，就是真实文本
文件体积大（图片）小
分页要自己算高度切图，很容易把一行字切成两半浏览器排版引擎处理，自动分页
代码量几百行十几行 + CSS
依赖两个几百 KB 的库零依赖
这里有个必须说清楚的事（简历里原来写错了）：

package.json 里确实装了 html2canvas 和 jspdf，但src/ 里一次都没引用过——是早期尝试留下的未使用依赖。真实导出走的是打印通道。简历上不能写"基于 html2canvas + jsPDF 实现 PDF 导出"，面试官让你打开代码就穿了。

怎么答

「导出 PDF 我最后选了浏览器打印通道，不是 canvas 截图。原因是问卷是文本为主的文档，canvas 方案会把文字变成位图，不可搜索、放大发虚、还要自己算分页容易切字。打印通道是浏览器排版引擎在干活，出来的是矢量 PDF，代码量也从几百行降到十几行。

导出前我做了一次白名单校验——不是所有题型都适合打印（比如评分星星的交互控件打出来会变形），所以先用一个类型守卫把题型名过滤一遍，有不合规的就提示用户先移除，而不是硬导出生成一份残缺的 PDF。」

那个白名单是什么

src/types/material.ts 
97const useForPDFComNameArr: Material[] = [
98  'single-select', 'multi-select', 'single-pic-select',
99  'text-input', 'text-note', 'personal-info-name', ...
119]
120export function isUseForPDF(value: string): value is SurveyComName {
121  return useForPDFComNameArr.includes(value as SurveyComName)
122}

注意返回值写的是 value is SurveyComName，这叫类型谓词。它告诉 TypeScript："如果你这个函数返回 true，那这个参数就是 SurveyComName 类型"。这样调用处就能获得类型收窄，而不是只知道"是个 boolean"。

11发布与答题：后端 4 个接口和降级

它解决什么问题

这就需要一个后端存问卷、收答卷。但现实是：这个项目多数时候跑在没有后端的静态环境里（比如部署到静态托管做演示）。如果后端不在，点"生成链接"直接报错，整个 demo 就废了。

后端只有 4 个接口

问题改法
数据存内存，进程一重启问卷和答卷全丢改成启动读盘、每次写入落盘到 data/*.json，写入用「临时文件 + rename」保证原子性——避免写到一半被杀留下半个 JSON，下次启动解析失败

三处降级：让没有后端也能演示

怎么答

12我踩过的两个真坑

面试最值钱的部分不是"我做成了什么"，是"我卡在哪、怎么出来的"。下面两个都是真实发生过的，有代码可查。

坑一：循环依赖导致整站白屏

现象：本地 vite build 完全通过，但打开页面一片白，控制台只有一行 ReferenceError: Cannot access 'us' before initialization。

原因：我在新加的 db/seed.ts 顶部静态 import 了题型工厂，工厂又 import 各自的 Vue 组件，组件又反向依赖 stores 和 utils，和 HomeView → seed 这条链组成了循环依赖。构建工具能打包，但运行时模块初始化顺序被打乱，某个变量在被赋值之前就被访问了（TDZ，暂时性死区）。

解决：把静态 import 改成函数内部的动态 import()，把这条链推迟到应用挂载之后执行，循环就断开了。

怎么定位的：压缩后的报错只有单字母变量名，看不出是哪个模块。所以接了 CDP 抓浏览器控制台的异常堆栈，才定位到入口 chunk。

坑二：IndexedDB 存不了函数

现象：预置示例数据时抛 DataCloneError，错误信息在生产构建里被打包工具压缩成了单字母。

原因：Status.type 是 markRaw 包过的 Vue 组件对象，IndexedDB 的结构化克隆不支持函数。

解决：照项目原有的约定，落库前先 JSON.parse(JSON.stringify(...)) 把组件字段丢掉，只留 name；读取时 restoreComponentStatus 按 name 查 componentMap 补回来。

额外收获：发现 JSON.stringify 把组件变成了 {} 而不是删掉这个字段，所以"为空才补"的判断是失效的，必须无条件覆盖。

讲坑的正确姿势：现象 → 排查过程 → 根因 → 方案 → 学到什么。五步缺一不可。只说"我遇到了一个 bug 然后修好了"，等于没讲；把"怎么定位的"讲清楚，才显得你会调试。

13面试预演：20 问 20 答

按被问到的概率排序。答法都是口语，可以直接念。

为什么用 Pinia 不用 Vuex？
Vuex 要写 mutation，改状态得先 commit，一个简单操作要跨两个地方改。Pinia 去掉了 mutation，action 里直接改 state，而且对 TypeScript 支持是原生的——不用为了类型推导写一堆额外声明。这个项目状态结构比较复杂（嵌套的 status 对象），用 Pinia 的类型体验明显更好。
markRaw 是干什么的？为什么到处都在用？
它告诉 Vue"这个对象不要做成响应式代理"。组件对象被 proxy 包一层之后，性能会白掉，而且会导致组件身份比较失效、拖拽时可能触发递归更新。凡是不会变的对象——组件、图标、配置常量——都应该 markRaw。
你项目里有没有做性能优化？
有，但不算多。一是路由级懒加载，编辑器、预览、答题页都是 () => import() 按需加载，首屏不用把编辑器代码下载下来。二是组件用 markRaw 避免无谓的响应式代理。三是属性面板是 v-for 渲染的，每一项都带稳定 id 做 key，避免增减选项时复用错的 DOM。做得不够的地方是主包还是偏大，Element Plus 全量引入了，如果继续优化会改成按需引入。
为什么选项至少保留两个？删到一个会怎样？
单选/多选只有一个选项没有意义，问卷逻辑上就废了。所以 removeOption 里做了判断：status.length === 2 时直接返回 false，dispatch 那层根据返回值提示"至少保留两个选项"。这是把业务规则收在 action 里，而不是散在各个 UI 组件里。
题目编号是存在数据里的吗？
不是，是算出来的。useSurveyNo 遍历 coms，只在"是题目类型"的位置递增计数器，备注说明这类非题目组件返回 null。好处是删掉中间一道题，后面编号自动前移，不需要手动维护一个 number 字段——那种做法的数据一致性维护成本很高。
拖拽排序怎么实现的？
用 vuedraggable，v-model 直接绑 store 里的 coms 数组。所以拖动结束时数组顺序就变了，不需要额外的"同步"逻辑。DOM 上的 key 用的是每道题自己的 id 而不是数组下标——用下标的话，拖动后 Vue 会复用错误的组件实例，输入框里的光标位置这类内部状态会串。
你的属性面板为什么只有 12 行？不可能吧。
真的只有 12 行，核心就是一个 v-for 加一个动态组件。v-for 遍历这道题的 status，每一项自带 editCom 字段说明"用哪个控件编辑我"，然后 <component :is="item.editCom"> 渲染出来。面板本身不认识任何具体控件，所以 30 种题型共用这一套。这是数据驱动的收益。
那 config-key 是干嘛的？不传行不行？
不行。因为有些控件是复用的，比如 titleSize 和 descSize 用的是同一个 SizeEditor，选项值完全一样，只是作用对象不同。控件必须知道"我在改的是 titleSize 还是 descSize"，所以父级得把 key 传进去。
为什么改一个属性要绕这么多层（updateStatus → dispatch → action）？直接改 store 不行吗？
直接改的话，十几种控件就有十几种改法，而且"必须先选中组件"这种前置校验要在每个控件里写一遍。收口到一个入口之后，校验只写一处，类型分派只在 dispatch 里做一次，UI 组件只负责发消息不负责改数据。代价是链路长了一点，但可维护性好很多。
options 那一堆 if-else 判断 payload 类型，是不是设计得不好？
这是权衡。选项这一块有四种操作——增、删、改文字、启用禁用——改的是同一个字段，开四个入口会把面板和 store 之间的接口撑大。所以用载荷类型区分意图。知道它的缺点：可读性一般，新人接手要对着注释看。如果重做，可能会拆成 updateOptions(action, payload) 这样显式带操作类型，比靠类型猜更清楚。
为什么用 TypeScript 还要写那么多 isXxx 判断？
因为类型在运行时全部消失，TypeScript 只是编译期约束。数据可能来自 IndexedDB、来自后端接口、来自用户输入，运行时什么都可能发生。所以关键入口要做运行时校验。那些 isXxx 是类型谓词函数，返回值写成 value is SomeType，这样校验完 TypeScript 还能自动收窄类型，一举两得。
为什么存 IndexedDB 不存 localStorage？
三个原因：容量、类型、阻塞。localStorage 只有 5MB 左右，问卷里带 base64 图片很容易爆；它只能存字符串，每次都要手动序列化；而且它是同步 API，大一点的数据会卡主线程。IndexedDB 容量大、支持结构化克隆、全异步还有索引。Dexie 是在上面封了一层 Promise 化的 API，写起来比原生 IDB 舒服太多。
我看到你存的时候做了 JSON 序列化，为什么？
因为数据里有 Vue 组件对象，IndexedDB 的结构化克隆不支持函数，直接存会抛 DataCloneError。序列化一次等于"深拷贝但只保留能被 JSON 表达的部分"，组件字段就被过滤掉了，只留 name 字符串。
那读回来组件怎么办？
按 name 查表补回来。restoreComponentStatus 里遍历每道题，用 componentMap[com.name] 还原 type，用 componentMap[status[key].name] 还原每个编辑控件。这里有个坑：stringify 之后 type 不是被删掉而是变成了空对象 {}，所以判断"为空才补"是失效的，必须无条件覆盖。
你的编辑器有两个 store，为什么要两个？
编辑器和组件市场是两个场景：编辑器操作"数组里某个位置的题"，市场操作"当前选中的那一个题型"。数据结构不一样，但操作逻辑完全一样。所以拆成两个 store 各自管数据结构，共用同一套 actions 接口，再用一个 useStore() 按当前视图动态返回实例。这样 dispatch 那层的分派逻辑只写一份。
useStore 读 localStorage 会不会有问题？
会，这是我的一个已知弱点。它依赖 localStorage 这个隐式状态，如果值不匹配两个 case 会返回 undefined，调用方就炸了。更稳的做法是把视图类型放进路由 meta，或者用 provide/inject 显式传，而不是读全局存储。当时为了快速跑通选了简单方案，这是要还的技术债。
PDF 导出怎么做的？
走浏览器原生打印通道，window.print() 配合 @media print 隐藏操作区和边框。没用 canvas 截图方案，因为问卷是文本为主的文档，截图会把文字变成位图——不可搜索、放大发虚、还要自己算分页容易把一行字切两半。打印通道出来的是矢量 PDF，代码量也少一个数量级。
那 package.json 里的 html2canvas 和 jspdf 是干嘛的？
早期尝试留下的，后来改用打印通道就没删。实际代码里没有任何引用，是我的疏忽——应该清掉。这也说明依赖清单要定期清理，留着会让人误判技术方案。（这题如果被问到，大方承认，比找理由强。）
后端为什么只有 4 个接口？是不是太简单了？
是刻意保持简单的。这个项目的定位是前端低代码编辑器，后端只承担"问卷分发"这一件事：存问卷、取问卷、收答卷、传图片。编辑逻辑、渲染、PDF 导出全在前端。这样做的好处是后端挂了编辑器照样能用。我在后端做的改进主要是持久化——原来是内存变量重启就丢，改成落盘 JSON，写入用临时文件加 rename 保证原子性。
如果让你重做，你会改什么？
三件事。一是把 useStore 依赖 localStorage 改成依赖路由 meta，去掉那个隐式状态。二是 options 那块靠 payload 类型分派改成显式的操作类型，可读性更好。三是把导出白名单、题型枚举这些"散在类型文件里的业务清单"抽成配置，现在是硬编码数组，加题型容易漏改。另外主包偏大，Element Plus 应该改按需引入。

14不能说的话（简历与讲解红线）

这一节比前面所有节都重要。面试官不会因为你某个技术点讲得浅而否掉你，但会因为发现你说的话和代码不符而直接否掉。以下几条，一条都不能碰。

❌ 不能说真相 / 该怎么说
「基于 html2canvas + jsPDF 实现 PDF 导出」 这两个库代码里一次都没引用。实际是 window.print() + 打印样式。要说"基于浏览器打印通道导出 PDF，配合题型白名单校验"。
「打通创建-编辑-预览-发布-回收全链路闭环」 后端只有 4 个接口、72 行，且原来存内存。"全链路闭环"这个词太重了，容易被追问架构。改成"前端完成创建-编辑-预览-导出全链路，服务端提供问卷分发与答卷回收接口"。
「实现了用户体系 / 权限管理」 项目没有登录注册，问卷归属靠浏览器本地数据。一个字都不能提。
「用了 WebSocket 做协同编辑」 没有任何 WebSocket。虽然有个 EventBus 文件，但那是组件间通信用的，跟实时协同没关系。
「数据库设计 / 索引优化」 后端是 JSON 文件，没有数据库。前端 IndexedDB 只有一张表三个索引（createDate / updateDate / title / surveyCount）。说"设计了 IndexedDB 表结构"可以，说"数据库设计"会被追着问到崩。
「支持 30+ 题型」 数字没问题（SurveyComName 里 25 个题型 + 备注说明 = 26 种组件，算上 12 个编辑控件是 38 个）。但别把编辑控件也算成题型，被问"哪 30 种"会数不出来。稳妥说法："20 多种题型"。
「高并发 / 性能压测」 没有任何压测数据。这个项目的量级根本谈不上并发。
一条通用原则：凡是简历上写了、但你说不清"具体在哪个文件第几行"的东西，一律删掉或者改弱。能讲透三个点，比罗列十个点值钱得多。
